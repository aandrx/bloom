# Source-publication licenses and notices

Status: evidence record for the source-publication review. It separates what the
repository contains from the decisions the owner and qualified reviewers still
have to make. It is not legal clearance and does not change repository
visibility.

This record covers the source tree. Binary packaging obligations are recorded
separately in the [B-4c release paperwork](packaging-4c-release-paperwork.md).
Passing a source check does not resolve a binary obligation, and the reverse is
also true.

## Bloom's own source

- [`LICENSE`](../LICENSE) at the repository root contains the MIT text with the
  holder recorded as "Bloom contributors".
- The root `Cargo.toml` declares `license = "MIT"` in `[workspace.package]`.
  `cargo metadata --no-deps` reports MIT for all seven workspace packages:
  `bloom-core`, `bloom-domain`, `bloom-secrets`, `bloom-ipc`,
  `bloom-transport`, `bloomd` and `bloom-tui`.
- The owned Dart code lives in `ext/bloom-engine-sidecar/dart`, which declares
  `publish_to: none`. It has no package-root `LICENSE` of its own and falls under
  the repository license. A package-level copy would make the tree portable when
  copied out of the repository. That is an optional improvement, not evidence
  that the code currently has no license.
- Copyright holder wording is an owner decision. Do not invent additional
  holders.

## Generated OpenBubbles bindings

The bindings under `ext/bloom-engine-sidecar/dart/lib/upstream/` come from
OpenBubbles release tag `v1.15.0+205`, commit
`852c9910f456492f7f840ac4ff2a8bad7a1ee8c8`.

- `lib/upstream/LICENSE` contains the stock Apache License 2.0 text.
- `lib/upstream/NOTICE` is Bloom's added attribution. It names the upstream
  project, tag and commit, and links the license copy.
- `ext/bloom-engine-sidecar/ATTRIBUTION` records the same pin and that the
  bindings are Apache-2.0.

Primary sources checked:

- Upstream license at the pinned commit:
  <https://raw.githubusercontent.com/OpenBubbles/openbubbles-app/852c9910f456492f7f840ac4ff2a8bad7a1ee8c8/LICENSE>
  contains the Apache License 2.0 text.
- The pinned root tree at the same commit, queried through the GitHub API,
  contains `LICENSE` and no root `NOTICE`.

The applicable Apache-2.0 conditions are:

- 4(b): files that were modified must carry prominent notices stating the change.
- 4(c): retain all copyright, patent, trademark and attribution notices from the
  source form, excluding notices that do not pertain to the derived work.
- 4(d): reproduce an upstream `NOTICE` only when the source form includes one.
  The pinned root has none, so the current Bloom `NOTICE` is an attribution aid,
  not a required upstream notice.

A parent-run byte comparison of all five committed Dart files against the pinned
upstream source found `api/api.freezed.dart` identical. The other four files
(`api/api.dart`, `frb_generated.dart`, `frb_generated.io.dart`, and `lib.dart`)
match the pinned originals after formatting temporary copies with Dart 3.13.4.
The tracked generated files were not changed. The formatter cannot parse the
unchanged upstream Freezed output in that temporary context, so that file was
verified by direct byte equality instead.

The four formatting differences are real modifications, not evidence of a
different engine API. The approved refresh helper's `--notice-current` mode now
adds an explicit modified-distribution comment to all five staged files. A
parent-run before/after hash check confirmed that every original Dart body and
both attribution files remained byte-identical. The helper, not a hand edit,
made the change. Apache 4(b) file-level modification notices are now present.
No upstream copyright holder or missing upstream notice was invented.

## Spike packages

`spike/gpui` and `spike/matrix` are separate research crates. Neither has
package-level license metadata. That absence is not by itself evidence that the
root license does not apply, and it is not evidence that the spikes are excluded
from the source publication. An owner or reviewer should decide whether to add
metadata, exclude them, or state their status in the publication description.

## Third-party notice bundle

`third-party-notices/` is generated by
`scripts/generate-third-party-notices`. It currently records 485 Rust packages
and 52 resolved Dart packages, with 48 Rust packages using generic fallbacks.

- All 52 current Dart manifest entries have notices. `NO FILE` is a state the
  generator can emit when a package ships no license file; it is not a current
  finding in the committed manifest.
- A generic fallback text is not a substitute for package-specific copyright
  notices. The fallback list and the MPL-2.0, Unicode-3.0 and compound
  expressions still need review for binary distribution.
- No bundle edits are required for this source review.

`scripts/stage-prefix` plans `share/bloom/third-party-notices` in the staged
prefix. The earlier B-4c staged-contents list omitted that path; the script is
the source of truth.

## Runtime engine boundary

- No engine binary is tracked or staged.
- A fresh `cargo tree` for the default daemon dependency graph contains no
  `rustpush`.
- A user-supplied runtime engine may contain SSPL and closed-source components.
  The Rust daemon communicates with the Dart child and has no link dependency on
  the engine. The Dart child loads the engine through FFI at runtime.

The inventory facts above are separate from the legal question of what those
components require. A process boundary is an engineering control, not a legal
exemption, and no legal signoff has been obtained. The external-engine review is
still open for both source and binary publication.
